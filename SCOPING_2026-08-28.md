# djbot — scoping: harmonic mixing + hybrid transition engine

Scoped 2026-08-28, grounded in the real pipeline (`mixer/analyze.py`,
`mixer/beatgrid.py`, `mixer/transition.py`, `mixer/set_builder.py`,
`CLAUDE.md`). Planning only — nothing implemented.

---

## 1. Harmonic mixing (Camelot Wheel key compatibility)

### Current state
`mixer/analyze.py` does BPM + beat-timestamp extraction only, via
`librosa.beat.beat_track()` and onset-strength envelope — there is **no
key/pitch detection anywhere in the pipeline**. `beatgrid.py` layers a more
accurate beat detector (`beat_this`, CPJKU) and a beatgrid cache on top of
this, still tempo-only. Track ordering into a set currently has no harmonic
signal to draw on at all — brains (`brains/*.py`) presumably order tracks by
curation/BPM flow only.

### Proposed approach
- **Key detection**: add a `detect_key()` step to `analyze.py` using
  librosa's chroma features (`librosa.feature.chroma_cqt` or
  `chroma_cens`) → Krumhansl-Schmuckler key-profile correlation, the
  standard cheap approach. This reuses the same loaded audio (`y`, `sr`)
  already in memory in `analyze()` — no new audio load, just an added
  computation on data already there. Cache the result in
  `beatgrid_cache.json` alongside BPM (same cache pattern already used).
- **Camelot mapping**: standard fixed lookup table, musical key → Camelot
  wheel position (e.g. `Am` → `8A`, `C` → `8B`) — this is a static
  ~24-entry dict, no library needed.
- **Compatibility scoring for set ordering**: Camelot-adjacent keys (same
  number ±1, or same number switching major/minor letter) score as
  compatible; anything else scores as a clash. Feed this into whatever
  currently orders tracks in `set_builder.py`/the brain files as an
  additional soft signal alongside BPM flow — a scored ranking, not a hard
  filter, since djbot's existing curation logic likely has other
  priorities (energy arc, etc.) that shouldn't be overridden by key alone.

### Effort estimate
**Small-medium.** Key detection itself is a small, self-contained addition
(one function, reuses already-loaded audio, no new dependency — librosa is
already a hard dependency). The larger unknown is wiring compatibility
scoring into set ordering without disrupting the existing curation logic in
the brain files, which weren't read in this pass (`brains/*.py`) — that
integration point needs its own look before estimating tightly.

### Risks / open questions
- Chroma-based key detection is noticeably less reliable on tracks with
  ambiguous tonal center (a lot of techno/tech-house — which is most of
  what djbot mixes per the solomun/adana/butch track names in CLAUDE.md —
  can be modal or drone-based rather than clearly major/minor). Confidence
  scoring alongside the key guess is worth adding from the start, mirroring
  the existing `low_confidence` pattern already used for BPM in
  `set_builder.py` (`grid_a.get("low_confidence")` gates straight to a hard
  cut) — a low-confidence key should probably just be excluded from
  scoring, not trusted.
- This changes track *ordering*, not the transition-building logic itself
  — the existing phase-error/RMS quality gates and BPM-ramp system are
  unaffected. Low risk to the audio-correctness rules in CLAUDE.md's
  "NON-NEGOTIABLE" section.
- djbot's own hard rule to keep compute cheap applies — chroma extraction
  on a full track is not free; consider running it only once per track at
  ingest/analyze time (already the pattern for BPM), not per-transition.

### First concrete step
Add `detect_key()` to `analyze.py`, run it against the existing solomun set
track list (already fully analyzed/cached per `beatgrid_cache.json`), and
print the resulting Camelot keys next to the known-good transition order in
CLAUDE.md's "Which transitions get ramped (solomun set)" table — a cheap
sanity check on whether the existing hand-curated order already tends
toward compatible keys (it may well, if the curator has a good ear) before
building any scoring/ordering logic on top.

## 2. Hybrid beatmatch/crossfade transition engine

### Current state
`set_builder.py`'s `build_one_transition()` already has a **3-tier
decision**, not a binary one:
1. `diff_pct <= max_bpm_diff_pct` (default **8.0%**) → normal beat-matched
   blend with the BPM ramp system (last 8 bars, 32 chunks — see CLAUDE.md).
2. `8.0% < diff_pct <= MAX_BRIDGE_DIFF_PCT` (**35.0%**) → `bridged = True`,
   still a full beat-matched blend but presumably with more aggressive
   time-stretching to force the larger gap closed (the `bridged` flag is
   set but this pass didn't trace where it's consumed downstream).
3. `diff_pct > 35.0%` → `_build_hard_cut_transition()` — no beatmatch
   attempt at all, a hard cut with an `_echo_out_tail()` (not silence, an
   echo decay — see `ECHO_OUT_BEATS`).

There is also a separate low-confidence path: if either track's BPM/beat
detection is itself unreliable (`grid.get("low_confidence")`), it skips
straight to a hard cut regardless of the numeric diff_pct — a real,
already-battle-tested instance of "don't trust the number, trust the
signal that produced it," directly matching CLAUDE.md's HARD RULE that a
passing phase-error number is not proof beats actually sound matched.

### Proposed approach
The gap this idea actually points at: **tier 2 ("bridged")** is where a
lot of time-stretching happens to force a beat-matched blend across up to a
35% tempo difference — that's a large stretch (e.g. 120→155 BPM) and likely
where pitch/tempo artifacts are most audible, more than tier-1's small
ramps. A genuine hybrid engine would split tier 2 into two sub-cases
instead of always forcing a full stretched beatmatch:
- **Close end of tier 2** (e.g. 8–15% diff): keep the existing bridged
  beatmatch approach — stretch is still modest enough to sound clean.
- **Far end of tier 2** (e.g. 15–35% diff): fall back to a plain
  equal-power crossfade with **no forced beatmatch** — accept that the
  beats won't lock, but avoid the audible pitch/time-stretch artifact a
  large forced stretch produces. This directly matches Louis's own
  2026-08-19 hard rule in CLAUDE.md: *"if you don't match the beats
  NOTHING matters... the hard-cut + echo-out fallback is the CORRECT,
  PREFERRED choice"* — the existing rule already establishes the
  philosophy this idea would extend one tier earlier, with a softer
  (crossfade, not hard cut) fallback for the specific case where a
  forced stretch would be the worse artifact.
- Threshold between the two sub-cases should be tuned by ear against real
  sets, not guessed — start conservative (bias toward the existing bridged
  behavior) and only widen the crossfade-only zone if a real listened
  transition confirms the forced stretch sounds worse.

### Effort estimate
**Medium.** The 3-tier skeleton and both audio primitives already exist
(beat-matched blend, hard-cut+echo). This is mostly: (a) tracing where
`bridged` is consumed to understand what "aggressive stretch" currently
looks like, (b) adding one new code path (plain crossfade, no stretch, no
BPM ramp) as a real third option, (c) picking and validating the sub-tier
threshold against real material.

### Risks / open questions
- This must not weaken the existing non-negotiable audio-timeline rules
  (never repeat, never skip, never cut without a crossfade) — a
  crossfade-only fallback still needs the same 5ms micro-crossfade/RMS
  continuity discipline already enforced elsewhere, just without the BPM
  ramp step.
- Needs real listening tests, not just the numeric phase-error/RMS gates —
  CLAUDE.md is explicit that passing gates isn't proof of a good-sounding
  transition (the Corona→Real McCoy 0.1ms-phase-but-audibly-wrong case is
  the documented example). Any new tier needs the same by-ear validation
  before being trusted.
- Where the sub-tier threshold should sit is a real open question, not
  something to guess from first principles — needs testing against
  existing library material with genuinely large tempo gaps.

### First concrete step
Trace what `bridged=True` actually changes in the downstream build path
(the part of `build_one_transition` after line ~452, not read in this
pass) to confirm what "aggressive stretch" currently sounds like — then
pick 2-3 real track pairs from the existing library with a diff_pct in the
15-35% range and render both the current bridged-beatmatch version and a
plain-crossfade version side by side for a real listening comparison before
writing any threshold-based branching logic.
